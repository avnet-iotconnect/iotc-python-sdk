# Telemetry payloads, command types and acknowledgements

## Telemetry (D2C) with `SendData`

`SendData` takes a **list**. Each item is one device's reading:

```python
[{
    "uniqueId": "<device unique id>",           # the device, or a child of this gateway
    "time": "2026-11-05T10:06:17.000Z",         # UTC, YYYY-MM-DDTHH:MM:SS.000Z
    "data": {"temperature": 21.5, "gyroscope": {"x": -1.2}}
}]
```

Generate the time with `datetime.now(timezone.utc).strftime("%Y-%m-%dT%H:%M:%S.000Z")`.
All three keys are required: a missing one makes the call fail and send nothing.

### What `SendData` returns

| Return | Meaning |
|---|---|
| `True` | published |
| `False` | publish failed (offline; buffered if offline storage is on), or no item matched a known device |
| `None` | nothing attempted: before `onReady`, after a barred/disabled/released/stop command, inside the data-frequency window, after `Dispose()`. **Also** when the payload makes the SDK fail: a missing `uniqueId`/`time`/`data`, `data` not a dict, a non-dict for an OBJECT attribute, or a `dataValidation` the SDK cannot parse |

Treat only `True` as sent. Every row is covered by `tests/test_sdk_behaviour.py`.

### Gateway with children

Put one item per device in the same list. Each child may send only the attributes of its tag. See
`gateway-and-children.md`.

### How keys are matched

- A key in `data` is matched to a template attribute by its **name** (case-sensitive).
- OBJECT attributes are nested: `{"gyroscope": {"x": 1.2}}`.
- Matching keys with valid values are sent as normal reporting telemetry (RPT).
- Unmatched keys, and matching keys with invalid values, are sent as a **separate FLT message**.
  They do not appear as the device's normal attributes. Compare the key and type to the template first.
- A key whose value is `None` is dropped silently.
- Values are checked against the template types and `dataValidation` unless `skipValidation` is `True`.

### Data frequency (the most common "missing data" cause)

The platform sets how often a device may report (`ct` 105 updates it at run time; the SDK default is
60 seconds). For non-edge devices the SDK **drops** any `SendData` call made before the current window
ends and returns `None`. Sending every 10 seconds against a 60-second window delivers about one call in six.

Send at the configured interval, check for `True`, and use `IsDebug` while testing. Do not retry in a
tight loop on `None`.

### Other behaviours

- Never call `SendData` from inside the `onReady` callback. The SDK calls `onReady` just before it
  attaches its validators, so that send goes out entirely as FLT (tested). Wait for `onReady` in the
  main thread, then pause about a second.
- The SDK prints `rtp:` and `flt:` lines on every send, whatever `IsDebug` says.
- Offline storage buffers data while disconnected, if enabled in `SdkOptions`.

## Command types (C2D)

Taken from `CMDTYPE` and `onMessage` in `IoTConnectSDK.py`:

| `ct` | Meaning | What the SDK does |
|---|---|---|
| 0 | device command | calls `onDeviceCommand` |
| 1 | firmware update (OTA) | calls `onOTACommand` |
| 2 | module command | calls `onModuleCommand` |
| 101 | attribute change | calls `onAttrChangeCommand`, re-syncs |
| 102 | setting change | re-syncs |
| 103 | rule change | calls `onRuleChangeCommand`, re-syncs |
| 104 | device change | re-syncs the device list |
| 105 | data frequency | updates the frequency, no callback |
| 106 / 107 / 108 / 109 | barred / disabled / released / stop | disconnects and clears offline storage, no callback |
| 110 / 111 | start / stop heartbeat | handled internally |
| 112 / 113 | video stream start / stop | handled internally, no callback |
| 116 | connection status | generated by the SDK's MQTT client and passed to the constructor callback |

The platform reference table (docs.iotconnect.io/sdk/custom/reference-table) lists different numbers
for the change commands (116 attribute change to 121 hard stop). This SDK does not use those numbers.
Callbacks fire as in the table above.

## Acknowledging commands

A command can carry an `ack` field (a GUID). If it does, the platform expects an acknowledgement.

```python
def on_device_command(msg):
    ack = msg.get("ack")
    ok = run(msg)
    if ack:
        Sdk.sendAckCmd(ack, 2 if ok else 1, "executed" if ok else "failed", msg.get("id"))
```

- Pass the child id as `childId`, **as a string**, when the command is for a child. An unknown or
  non-string id makes the SDK send nothing (tested).
- `ack` may be `None` (commands raised by edge rules); calling the ack methods with `None` raises.
- Print the first command you receive to learn the field names for your platform version.

### Status values

The SDK passes `status` through unchanged (`sendAckCmd` sets `type` 0, `sendOTAAckCmd` sets `type` 1;
both publish on the acknowledgement topic). The values are the platform's, from the device message 2.1
reference table (docs.iotconnect.io/sdk/custom/reference-table):

| `sendAckCmd` | Meaning |
|---|---|
| 0 | executed, result unknown |
| 1 | failed |
| 2 | executed successfully (executed ack) |

| `sendOTAAckCmd` | Meaning |
|---|---|
| 0 | executed (cloud only) |
| 1 | failed (download or install) |
| 2 | downloading |
| 3 | download done |
| 4 | download failed |
| 5 | **success**: firmware applied |

**OTA success is 5.** The SDK sample uses 5. The README's OTA example says `0` is success, which is
wrong according to the platform table: 0 means "executed (cloud only)". The sample's older comments
(`st = 6`, `st = 7`, `st = 4`) are out of date. This was checked against the platform table
and the SDK code. It has not been confirmed against a live platform.

A typical OTA flow: ack 2 when the download starts, 3 or 4 when it ends, then 5 or 1 after applying.

### Twin

1. Register `onTwinChangeCommand(cb)` and call `getTwins()`.
2. The callback receives `{"desired": {...}, "uniqueId": ...}`. Skip `version`.
3. Convert each value to the setting's type, apply it, then report it with `UpdateTwin(key, value)`.

`UpdateTwin` sends nothing for keys that are not settings in the template. It checks the value **only
when the setting has a `dataValidation`**. Then a wrong type (for example the text `"0"` for a BIT)
is dropped silently. Without one, any value is sent as given, including text for a number setting
(tested). Always convert: the skeleton from `template_tool.py` prints a converter per setting.
